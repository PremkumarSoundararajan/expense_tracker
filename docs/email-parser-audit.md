# Review of the email expense detection notes

**Follow-up:** Parser version 4 now adds ranked payment labels, received/posted/thank-you completion phrases, positive paid-label evidence, user-timezone dates and a visible Needs review inbox with reasons and explicit manual confirmation. Candidate search is broader, and old skipped/pending review items can be re-evaluated by a lookback scan. See [email-detection-rules.md](email-detection-rules.md) for current behavior. The findings table below records the earlier audit, before this follow-up; entries about these features being absent are historical.

Checked against `pocket-ledger-api/src/email-receipts.js`, `email-capture.js`, and the Flutter review/import flow. Examples use synthetic receipts; no extra mailbox scan was initiated for this audit.

## Confirmed defects addressed in this change

| Finding | Reproduction / decision |
|---|---|
| Decimal-comma corruption | Confirmed: `€19,99` became 1,999; `EUR 1.234,56` became 1.23. The parser now validates the whole number token. Unsupported decimal-comma, space/apostrophe grouping, Indian grouping and more than two decimal places fail closed. Supported examples are `1234.56` and `1,234.56`; no locale is guessed. |
| `total` inside `subtotal` | Confirmed. A subtotal of 40 and total of 45 previously conflicted. Amount labels now have word boundaries: the result is 45. `discharged` is not an amount label. |
| Explicit dollar prefixes | `US$`, `C$`/`CA$`, `A$`/`AU$` and `S$`/`SG$` are now recognized when their currency is supported. Explicit currency outranks the mailbox default; conflicting explicit codes are rejected. Unsupported `NZ$`/`HK$`/`MX$` prefixes are rejected until those currencies are supported end to end. |
| Bare dollar assumption | A bare `$` still uses the mailbox default, but the proposal now carries `currencyNeedsReview`, displayed in the review screen. This is a warning, not FX conversion or reliable currency inference. Existing currency confirmation remains required. |
| Older unsafe drafts | Existing pending drafts from earlier parser versions are reconsidered on an explicit lookback scan. A draft that cannot be safely re-read is retained for exclusion, marked blocked, and cannot be approved. Older drafts without validated extraction evidence require a re-scan before a new append. Already-added, excluded and uncertain-in-flight records are not reinterpreted. Existing stable IDs can still confirm a previous successful write. This does not alter previously imported ledger rows. |

Tests cover the reported formats, explicit USD in a CAD mailbox, subtotal/total conflicts, refund exclusion, and blocking an old unsafe queued amount. These fixes do **not** implement the entire feature list below.

## Findings checked and remaining work

| Topic | Assessment and next step |
|---|---|
| Currency inferred from domain/country/language | Useful evidence for a warning, but not reliable enough to set currency alone. A US sender can bill CAD, and a Canadian merchant can bill USD. Prefer explicit currency in the charged amount; keep uncertainty visible. Not implemented beyond explicit prefixes and the bare-dollar warning. |
| UTC fallback date | Confirmed gap. Printed supported receipt dates take precedence, but fallback uses the received timestamp in UTC. Capture the user's IANA timezone and apply it to fallback dates; pin it for a resumed scan. A date-only receipt must not be shifted by timezone conversion. |
| `due`, refund and charged boundaries | The completion/rejection expressions already use word boundaries; `due` was not a substring-match bug. However, whole-word `due` or future-billing text can still reject a valid paid receipt. Separating payment evidence from unrelated future notices remains necessary. Amount-label boundaries are fixed above. |
| Refunds | Confirmed unsupported. They are currently excluded, not recorded as credits. Implement signed credits/refunds through Sheets storage, totals, budgets, duplicate matching, and UI together. Importing a refund as a positive expense would make spending less accurate. Existing ledger refunds were not adjusted by this audit. |
| 100,000,000-unit limit | It currently applies only to eight supported two-decimal currencies. IDR/VND/KRW are not parsed at all, so the example is a future-support requirement rather than a current misparse of those currencies. A wider currency set needs currency/minor-unit-aware validation across parsing, approval, dedup and formatting. |
| Candidate search | Confirmed narrow and English-only. Add invoice/order/booking/subscription/debit phrases and purchase-category candidates, but do not equate a search match with a completed payment. A known-sender list is a retrieval hint, not proof of a purchase or trusted sender. Search behavior was not broadened in this patch. |
| PDF and OCR | Confirmed missing. Add PDF text extraction with size/time limits, then OCR if needed. Linked receipts require a separate design; the parser should not fetch arbitrary links from email. |
| HTML cell/row boundaries | Already addressed: closing table cells/rows and other block boundaries become newlines, and remaining tags become spaces. The CVS HTML regression test exercises adjacent amount/label cells. More unusual layouts still need fixtures. |
| Charsets and multipart alternatives | Confirmed gaps. Content is decoded as UTF-8 and both text and HTML alternatives are collected. Honor declared supported charsets and choose a preferred usable alternative, with fixtures for ISO-8859, Shift_JIS and GB2312. Do not silently replace undecodable financial text. Not implemented here. |
| Amount label priority | A good direction, but not sufficient alone. `Subtotal 40 / Total 45 / Amount charged 30` can be a split-tender purchase: 30 is the card charge and 45 the purchase total. Define what the ledger records before automatically selecting 30. This patch resolves subtotal matching, while conflicting eligible totals still fail closed. |
| Bank/card alerts | Confirmed limited support. `debited`, `card used at`, regional UPI/card alerts and their references need explicit completion/transfer/hold rules. Add fixtures and compare them to receipts; avoid importing card-bill repayments as purchases. |
| P2P payments | Confirmed risk. `You paid Sam` can satisfy completion wording. Venmo/UPI/Zelle may represent a merchant purchase, transfer or reimbursement. Route ambiguous P2P items to review with a transfer classification; do not reject every regional payment rail. Not implemented yet. |
| Processor merchant names | Confirmed gap: sender fallback may be PayPal/Stripe rather than the seller. Add `receipt from {merchant}` extraction and processor-prefix normalization with collision tests. Shared merchant normalization exists, but this is not a complete processor-specific receipt resolver. |
| ISO currencies and minor units | Confirmed feature gap. Only USD/CAD/AUD/EUR/GBP/INR/SGD/MYR are supported. The parser, approval, duplicate tolerance and formatting currently assume two decimals. Adding JPY/KRW or KWD/BHD requires more than extending a dropdown. Unsupported currencies should stay blocked until then. |
| Foreign exchange | Confirmed major design gap. No conversion is performed and the Sheet has no original/home-currency/rate columns. Currency confirmation does not create an FX record. Choose a home-currency policy and store original plus billed amounts/rate/date before enabling mixed-currency imports. |
| Dates and calendars | Confirmed narrow: labeled ISO dates and the supported English retail date are recognized. DD/MM versus MM/DD must be locale-aware and flagged when ambiguous. Non-Gregorian dates require explicit conversion rules, not `Date.parse` guesses. |
| Locale packs and regional formats | Sensible next architecture. Use data-driven completion/amount/date/number rules and real anonymized fixtures per locale; prioritize actual user needs. Non-English receipts may currently fail at the search stage, before parsing. Not implemented here. |
| LLM extraction | Possible later fallback, not present now. Literal amount verification is necessary but insufficient: a model could select a balance or savings amount that really appears in the email. Validate amount role, currency, payment status, provenance and duplicates. Assess consent, data minimization and vendor data handling before sending any mail to another provider. |
| Fuzzy/date-window dedup | Confirmed current matching is brittle. Date/amount/normalized merchant is only a possible-match hint. Wider windows and fuzzy matching should flag candidates, never automatically discard repeated purchases. Use references and compare pending proposals as well as the ledger. Same-batch comparisons exist at approval; comprehensive pending-inbox matching does not. |
| Silent skips and skip reasons | Confirmed high-priority gap. A blocked legacy draft now gives an explicit reason, but new ambiguous messages still do not have a full Needs review list. Add per-email extraction outcomes and counts: examined, extracted, unreadable, ambiguous, non-purchase, duplicate. Store short evidence and reason codes, not full email bodies. |
| Re-evaluate skipped action | Parser-version changes already allow reconsideration during a new lookback. A dedicated re-evaluate action would be clearer; define its retained date range and pagination rather than silently expanding a user's requested scan. Not implemented yet. |
| Larger/background scans | Ten-message foreground batches and resume checkpoints already exist. Batch sizes can be tuned after measuring Worker request/runtime limits. Automatically moving scans into the background would conflict with the user's explicit earlier choice to keep scans user-started and foreground-only; retain that behavior unless requested otherwise. |
| Holds, free trials, unpaid bookings | Partially covered by scheduled/unpaid wording and positive-amount requirements, but no complete hold/authorization/settlement model exists. A booking or order confirmation is not always payment evidence. Add explicit statuses before broadening accepted completion phrases. |
| Sender authentication | Not implemented. SPF/DKIM/DMARC evidence can flag risk, but a pass does not prove a charge occurred. Do not trust arbitrary forwarded `Authentication-Results` headers or a sender-domain allowlist as authentication. Use trusted receiving-provider evidence and keep human approval. |
| Storage/privacy | Existing design encrypts refresh tokens and derived proposals, stores message IDs/short evidence, and does not persist raw bodies or attachments. Public Gmail restricted-scope verification remains separate. New PDF/OCR/LLM features need their own data-flow/retention review. This audit is not a certification of the app or its compliance. |

## Suggested implementation order

1. Deploy and exercise the amount/currency guardrails. Re-scan existing pending drafts in their original date range; review any already imported expenses separately.
2. Build a visible Needs review inbox, reason counts, mailbox timezone fallback and a re-evaluate-skipped action.
3. Broaden candidate retrieval and add common card/debit/processor fixtures without relaxing completion safeguards.
4. Design refunds, FX and ISO minor units together with the ledger schema.
5. Add PDF extraction and prioritized locale packs; consider OCR or an optional LLM only after measuring the remaining misses.
